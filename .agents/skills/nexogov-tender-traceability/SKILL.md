# Tender traceability

1. Treat the official edital, applicable errata, Termo de Referência, and accessible annexes in `docs/licitacoes/mata-de-sao-joao-91-2025/edital-original/` as the sources of truth. An erratum supersedes earlier wording only where it says so.
2. Cite document, printed page or PDF page, section, and item. Do not infer a requirement from OCR debris, a summary, a feature wishlist, or an implementation preference. For scanned pages, use OCR only for discovery and verify against the rendered source page.
3. Keep each source row and its unique ID stable. `MATRIZ_IDS.csv` is the persistent identity registry for numeric ED/TR rows; IDs are anchored to page and normalized source text, never to current row order. Edit the source scripts (`build-edital-matrix.py`, `extend-matrix-from-tr-ocr.py`, `render-traceability.py`) rather than hand-editing generated reports; preserve status/progress when regenerating unchanged rows. If an old source row disappears from parser output, retain its ID as `BLOQUEADO` for source review instead of deleting it or reusing the number.
4. Keep software, integration, operation/contract, company qualification, implantation, licensing/capacity, and POC obligations distinct. A code artifact cannot prove a contractual service or corporate qualification.
5. Every row needs source, priority, module, observable criterion, backend/frontend ownership, test, POC route, evidence, and one allowed status. `VALIDADO` requires the full criterion and verifiable evidence; otherwise use a truthful partial, pending, blocked, or justified non-applicable state.
6. Run `./dev matrix-refresh` after source/parser changes and `./dev matrix` to validate the result. Review changed rows and generated POC scenarios manually; a structurally valid CSV is not proof the transcript is complete.
   Generated summaries must count every status, including narrowly scoped `VALIDADO` rows. Report pending decomposition from the current acceptance criteria, and keep a statement that limited validations do not prove full tender compliance or completion of the official POC.
   When presenting a "non-software" total, include POC and commercial-proposal obligations or state explicitly that those categories are excluded; the nature breakdown and total must have the same scope.
7. Update `REQUISITOS.md`, `MATRIZ_ADERENCIA.md`, `POC.md`, risks, implementation plan, and increment evidence when the source or product state changes. Record inaccessible sources as blocked rather than claiming full review.
8. When a requirement combines implemented behavior with unfinished functionality, keep the source ID/status and describe both explicitly. Protocol subjects available only at the counter can be demonstrated separately from an unimplemented map/georeferencing clause; partial catalog proof must not imply that the map requirement is met.
   Assess sibling clauses independently: a separate pending participant-identity requirement does not automatically downgrade a fully tested completion/reopening clause. Cross-reference the pending ID in evidence, but set `VALIDADO` only when the literal criterion on that row is complete and tested; an internal test still does not stand in for the commission's official POC.
9. Treat `atividade(s)` as an ambiguous classification keyword. For a cross-cutting platform description such as “gerenciamento de atividades” without deadline/calendar context, use the existing `PLATAFORMA_E_ARQUITETURA` module. Add a matrix-check regression for confirmed false positives; do not remove a broad trigger without reviewing all affected IDs. When a module changes, regenerate its generic POC route while preserving manually maintained routes.
10. When the same capability appears in the edital and TR, review each operative clause in the official PDFs before comparing `natureza`; do not let a broad section heading or default classifier decide it. Classify periodic consultant pentests as `OPERACAO_CONTRATUAL`, EAD playback/assessment/certificate/progress functions as `SOFTWARE`, and company qualification evidence as `HABILITACAO_EMPRESARIAL`. Track provision of training material separately from EAD software behavior when the source wording distinguishes them. If media preference and content-delivery obligation leave different classifications, retain the source-specific classifications and explain the distinction; do not turn “preferencialmente em vídeo” into a mandatory video format. Preserve each source ID, text, page, and status.
11. Keep summary totals on a single row scope. A non-software subtotal must include POC and commercial-proposal rows or explicitly exclude them, and its detail categories must reconcile to the same subtotal. Report `PREFERENCIAL` separately when excluded from operational/non-software counts.
12. Treat POC conditions as historical once official procurement records show adjudication/homologation and a published contract. Preserve the old edital/errata rules as source evidence, but label schedules, email addresses, telephone numbers, and checklists as non-current; do not imply a new call or claim the winner's POC result without its report. State separately whether the new product under development has its own POC evidence.
13. Verify implementation-plan commands against `./dev help` before documenting local setup. Keep local build/E2E steps separate from contractual deployment, migration, training, support, and acceptance obligations.
14. Matrix summary checks must accept Portuguese thousands separators in manually maintained Markdown tables while comparing them with integer counts from the CSV; validate the check with the full current matrix, not a one-row fixture alone.
15. Keep product-security acceptance decisions distinct from source wording: when a clause does not prescribe an authentication mechanism or participant count, label individual credentials/isolation as the product's safe demonstration design, and label sample counts as test data rather than a contractual minimum.
16. A tested configuration sub-slice does not satisfy a combined requirement whose downstream workflow is absent. Record the implemented configuration, its backend/UI evidence, and the missing registration/access/interaction path separately; keep `EM_DESENVOLVIMENTO` until the source's complete criterion is exercised end to end. Reference the focused harness command and the remaining POC scenario in both the matrix and generated `POC.md`.
17. Visual E2E capture is supplemental evidence, never a status promotion. This harness exports only PNG screenshots explicitly attached by the evidence helper after a test passes; video stays off because continuous recordings can retain tokens or personal data outside targeted masks; raw Playwright reports and receipt PDFs stay out of the export. Allowlist the exact `(spec, scenario title)` pair and each attachment label. Capture the current viewport (`fullPage: false`) around an explicit focus locator; call `scrollIntoViewIfNeeded()` and assert visibility before capture so sticky navigation is not duplicated and the relevant state remains readable. Before a screen that contains a bearer field is captured, change that input to `type=password`, pass its locator to Playwright's screenshot `mask`, and assert the password attribute when a value is present. A source-level check can verify these preconditions but cannot prove pixel redaction; never search compressed PNG bytes for the raw token as proof. Inspect every exported image containing a bearer field visually. Map an edital ID only if the matrix explicitly cites that spec or a verified, unique harness-command chain, the ID is in the per-scenario mapping, and the scenario passed with an exported screenshot. State the capture's subflow and limits in the manifest; do not promote status or imply the full criterion/POC is proven. Unreferenced or ambiguous rows remain gaps. Use a fresh 0700 run directory under the user's Documents, refuse existing run IDs, write files as 0600, compare source and exported hashes, and keep media/reports outside Git and persistent Compose volumes. Never capture participant-access or OIDC token flows unless redaction is proven and reviewed.
18. Playwright's JSON reporter serializes in-memory `testInfo.attach({body})` image bytes as base64 in `attachments[].body`; path-based attachments may instead be copied to `data/` beside the report. Keep the private report inside the configured artifact root. Decode inline bodies strictly with a size limit and PNG signature check; accept file paths only when their resolved paths remain inside that same root.
19. A multi-screenshot scenario is complete only when every exact allowlisted label is present. A partial run may export its verified PNGs, but label-to-requirement mapping is per ID: associate only IDs whose required label set was actually captured and whose matrix row explicitly references the scenario. Record missing labels and leave unsupported IDs without media; never treat one screenshot as proof of sibling states or requirements.
20. For document-read clauses, separate a protocol-level inbox indicator from confirmation that a specific document or attachment was opened. Screenshot only the exact demonstrated state, retain `EM_DESENVOLVIMENTO` while the official acceptance criterion includes uncovered document-level, named audit, download-count, or other-module behavior, and list those gaps in the traceability row and evidence manifest. A screenshot collection for implemented slices does not imply that every edital requirement has a screen or proof.
21. Do not infer row-level visual review from a fixed page cutoff or OCR status. Compare each candidate's text with the rendered PDF page and surrounding paragraph/list structure, and keep a review ledger keyed by requirement ID, document hash, page, and decision before bulk-marking source status. Blank OCR lines can split one official paragraph into multiple candidate rows; when correcting a split, preserve both old IDs as blocked pending review and register the corrected source grouping without reusing an ID. Generic `Pendente de decomposição:` fields are not observable acceptance criteria; count them separately and do not call the matrix complete while any remain. The current TR page 52 candidates `TR91-0556` and `TR91-0557` require source-grouping review.
22. For contact-management clauses, preserve the official distinction between Edital `ED91-0130/0131/0132` and TR `TR91-0135/0136/0137`; the nearby list-creation clause is `ED91-0135`/`TR91-0140`, while vCard and duplicate merging have their own IDs. The words Financeiro and Suporte are examples of the municipal-department contact type, not support-service obligations. Keep each clause's source, module, test, evidence, and status independent; implementing contact types or CSV does not validate the official organogram, vCard, deduplication, contact lists, or the commission's POC.
23. Before preserving screenshots in Documents or using them as mapped tender evidence, inspect the actual exported PNGs for readable content, viewport position, unused empty space, and privacy masks. A passing E2E test does not make a badly composed screenshot acceptable evidence; adjust the real product layout, rerun the scenario, and retain the source hashes and per-ID limits.
24. For `TR91-0562`, cite the scanned Termo de Referência at PDF page 53, §7 `PROCESSO ADMINISTRATIVO`, and verify the sentence on the rendered source page. Keep this clause's acceptance limited to entering multiple identified process deadlines with due dates and retrieving the persisted values in stable order. Do not fold legal-day calculations, notifications, editing, SLA, process numbering, or the composite `ED91-0511` into this row. A local Testcontainers test, real-API Playwright scenario, and inspected screenshot may validate this software slice; they do not constitute official commission acceptance.
25. Requirement generators must never assign `VALIDADO` solely because an ID appears in an implementation mapping. Generate `EM_DESENVOLVIMENTO` until the acceptance test has passed and any claimed visual evidence has been exported and inspected; then record the evidence path and promote the matrix row explicitly. Preserve a previously recorded status on refresh without promoting it.
26. Do not dismiss a failed acceptance E2E as a flake because a later run passes. Preserve the failing values, request body when available, and browser/API diagnostic artifacts; if the failure artifact was lost or the cause is unknown, add focused diagnostics and keep the affected tender status unchanged. A separate, unrelated visual slice may still be documented on its own evidence.

For sensitive attachment evidence, keep the three viewport states separate: persisted subject rule, citizen upload/listing, and server-side list/download. Use fictional fixtures and the existing evidence helper; the citizen tracking credential must become a masked password field before capture, and no QR, login view, or request credentials may appear. Require configuration plus citizen upload only for IDs whose matrix text cites those actions; sector-access IDs can map to the server label alone when the row says so. Hosting clauses need both citizen and server UI states but remain partial while production storage/hosting is unverified. Never map a composite attachment-and-deadline ID from attachment screenshots alone; require exact per-ID labels and an explicit matrix reference. Validate the spec/config/exporter label sets, unique scenario titles, existing IDs and matrix links in `evidence-export-test`. S3Mock is a local API double, not proof of the real bucket or hosting operation.

For §14–15 document-access requirements, distinguish the protocol inbox receipt from per-document read events and attachment download counts. The staff panel must show tenant-scoped chronological events with actor type and date/time; public bearer access may be labeled by role only and must never be described as a verified identity. Do not say the audit requirement is complete while denied/anonymous access or system login attempts are missing. Map separate screenshot labels only to clauses actually visible in each viewport (for example, history vs total-download count), keep external identity and public history gaps explicit, and leave the affected rows `EM_DESENVOLVIMENTO` until their entire source clause has proof.

For `TR91-0561`, preserve the official §7 sentence and PDF page 53, and define its bounded acceptance as automatic numbering per subject or per organization's general sequence plus a custom public-administration pattern. Test both modes, including two subjects sharing the general counter, custom token validation, version inheritance/idempotency, configured timezone, concurrency, overflow, immutable issued numbers, and tenant isolation; inspect separate UI captures for each mode and a generated process number before setting `VALIDADO`. Existing processes keep their null number. Keep `ED91-0511` composite because it also includes multiple deadlines: the evidence exporter may associate that ID only after all numbering screenshot labels and the separate multiple-deadline screenshot are captured, with a negative test proving either incomplete group produces no association. `TR91-0561` and `TR91-0562` remain separately traceable; neither local result is official POC approval.

For `TR91-0149`, a protocol receipt QR that resolves to its bearer-authenticated tracking page is only a partial implementation of the clause covering every generated document. Keep the token in the URL fragment, remove it from browser history before the first API call, and mark the PDF `Cache-Control: private, no-store`. Pair a real-PDF QR decode test with a real-API browser test of the QR destination; capture only after URL cleanup and mask the visible credential field. Do not infer coverage of other document classes, signature validation, or the official POC, and keep the row `EM_DESENVOLVIMENTO` until the full source criterion has evidence.
