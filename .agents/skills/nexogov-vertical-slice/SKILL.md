# NexoGov vertical slice

1. Inspect the existing module and `docs/INCREMENTO_*.md`; reuse the current boundaries and identify the exact acceptance behavior before editing.
2. Resolve organization scope only from `TenantContext.requireTenantId()` or an equivalent server-validated context. Verify organization-level roles separately from sector membership. Filter every read, write, search, file, and audit record by that tenant.
3. Enforce authorization in the backend. A capability response may shape the UI but never replaces endpoint authorization. Use parameterized SQL and validate input at the API boundary.
4. For federated authentication, require HTTPS issuer and JWKS endpoints in production; allow HTTP only for loopback in test/local profiles. Validate signature, configured issuer, expiry/not-before, and audience using the trusted JWK source. Resolve only an active `(organization_id, issuer, subject)` link to an existing `user_accounts` row with `active=true`, then independently require active organization membership and no organization suspension on every protected request. Never auto-link by email or grant tenant permissions from provider roles. Block migration of global identity links when they map ambiguously to multiple organization-local accounts until authoritative reconciliation; never silently merge actors. Keep the generic NEXO Core contract for consumers whose external subject maps to one globally unique actor.
   A `OncePerRequestFilter` placed in Spring Security must be active only in the matching profile and must not also run as a servlet-container filter; preserve local Basic auth and avoid invoking identity resolution twice.
5. For organization access suspension, keep the override separate from `user_accounts`, `organization_memberships`, and `staff_memberships`; enforce it in the tenant-entry filter on every request so a previously authenticated identity loses access immediately. A sector `ADMIN` role is not organization administration. Serialize administrative access changes on the organization row and recheck actor authorization after the lock before protecting the last active organization admin.
   In staff UI, clear member data as soon as the selected organization changes and fetch it only after the server capability response allows organization administration. Render organization and department roles separately. A client-side last-admin check is only a usability guard: always submit permitted changes to the API and display its authorization or conflict response. Confirm suspension, provide direct reactivation, and close the local staff area and clear its credentials if the administrator suspends their own access.
   For repeated row actions, include the target person's name in each button's accessible name. Keep list-load failures separate from mutation failures; label a list refresh as a refresh, never as a retry of the rejected mutation.
   Provide an explicit staff sign-out that clears credentials and organization-scoped state from memory. Preserve the organization selector when the flow requires it across login/redirect; do not preserve loaded tenant data. Invalidate a monotonically increasing UI context generation on sign-out and tenant changes; every in-flight callback must check that generation and tenant before writing state, so late responses cannot restore data after sign-out or into a new context. Sign-out itself must not issue protocol mutations.
6. If persistence changes, add a forward-only Flyway migration. Detect unsafe legacy data before adding constraints; fail with a useful reconciliation message and do not rewrite records silently.
7. Keep public API changes in `contracts/openapi/`. Describe Bearer JWT for configured production and Basic only for the local profile; document tenant headers as selectors that do not grant access. Before UI changes, read `DESIGN.md` and the `nexogov-design-system` skill; consume the pinned `@nexo/core-ui` tokens instead of introducing an unrelated visual system. Keep the Vue/Quasar interface accessible, loading-aware, tenant-switch-safe, and explicit about success and failure.
   For forms that remain editable while a successful mutation refreshes a list or tree, clear only the submitted draft immediately after the server confirms success and before starting the refresh. Never clear it after `await refresh()`: the user may have started another draft while the refresh was pending. Cover this race by submitting one entry, starting the next draft while the refreshed item becomes visible, waiting only for the submit control to become actionable, and asserting the second draft and its selected parent survive before submitting it.
   When a citizen tracking link carries its bearer token in the URL fragment (including `#token=...` and existing QR links with `?token=...`), capture it and replace the current history entry before the tracking request. Preserve the path and query string, never log the token, and prove the link with a real-API browser test.
8. Add tests at the layer that proves the behavior: unit tests for isolated rules; PostgreSQL/Testcontainers for transactions, constraints, authorization, and cross-tenant denial; Playwright against the real API for member listing, suspension confirmation, reactivation, and tenant scoping. For organization access mutation, test both an actor with only a sector `ADMIN` role (403) and a target belonging only to another tenant (404), asserting no access-state or audit change. Test accessible names for repeated row actions. If an isolated UI test simulates a conflict response, identify it as simulated and keep the real API integration test separate. For access suspension, prove a later request using the same authenticated credentials is denied while department memberships and history remain intact. Do not mark requirements complete because a screen or mock exists.
   Integration tests that share a Testcontainers database must use deterministic fixtures: select only seeded departments or departments with explicit membership for the test actor, and remove temporary rows in `finally`. Do not let test execution order choose an authorization scope. When a PDF service normalizes display text, assert the normalized presentation rather than raw database whitespace unless normalization itself is under test.
9. Update the appropriate matrix rows and `docs/INCREMENTO_NN.md`. Use `EM_DESENVOLVIMENTO` for partial behavior; use `VALIDADO` only when the complete acceptance criterion and its evidence are verified.
10. Keep the development harness current: expose a focused `./dev` command for a costly or security-critical scenario so it can be repeated without knowing Maven internals. Run that command and `./dev verify-fast`; run `./dev e2e` when the change touches the UI or a user workflow.
11. Refresh this skill with reusable lessons from the increment. If its guidance remains accurate, record that check in `docs/INCREMENTO_NN.md`; do not leave skills, product docs, generated traceability, or harness instructions out of sync.
12. Inspect `git diff --check` and record exact outcomes and remaining limits.

For a browser OIDC client, use Authorization Code + PKCE as a public client with no client secret. Generate a fresh nonce for each redirect and require the OIDC library to validate it with the ID token; correlate state in session storage for the redirect transaction only. Require the exact configured callback origin and path, keep access/ID tokens in memory, and do not request refresh tokens unless a separately reviewed lifecycle requires them. Send only the access token as Bearer to staff APIs; never interpret provider email, subject, groups, or roles as a local identity or permission. Browser logout clears the client session and may redirect to the provider logout endpoint, but do not claim server-side access-token revocation. The backend remains authoritative for validated issuer/subject, active local account/link, tenant membership, suspension, and authorization. Enable Basic only by an explicit local development/E2E mode, with no production fallback when OIDC settings are missing or invalid. Keep public and staff API types/clients in separate import graphs and verify the citizen bundle contains neither Basic-auth helpers nor staff-only destination fields. OIDC Playwright with a simulated provider proves client mechanics only; backend integration tests separately prove API authorization. Document real IdP registration, claims, provisioning and operational limits as pending until verified against that provider.

For protocol participants, keep the applicant tracking token distinct from each participant credential. Generate a unique high-entropy bearer token per person, store only its digest, and return the raw token only in the successful creation response. Present a shareable link with the token in the URL fragment (not query or path), erase that fragment from browser history before the first tracking request, and do not log, persist, or send it to analytics. Resolve identity values against the selected tenant/subject's configured definitions while the subject row is locked, reject unknown/missing/invalid/oversized values before allocating a protocol number, and snapshot the definitions and answers under the new protocol. For any participant read, interaction, attachment download, or revocation, lock the protocol row before rechecking the active participant token; this serializes revocation with concurrent access and writes. A participant sees only their own identity values and no other participant record; public conversation labels for other participants must be neutral. Only the applicant token can enumerate participants or revoke their individual tokens. Do not let a participant token access another protocol or the applicant receipt. Token possession is not proof of civil identity: keep edital identity-provider requirements pending until the real provider, municipal credentials, and end-to-end identity path have been verified. Keep invitation delivery explicit; a one-time screen copy is not an e-mail delivery claim. Verify persistence, number-preserving rejection, token hashes, protocol scoping, participant anonymity, interaction writes and revocation with PostgreSQL/Testcontainers, then use `./dev participant-access-test` and `./dev participant-access-e2e` against the real API.

For protocol subjects, the organization catalog is authoritative: only an active organization `ADMIN` may configure it, and the public read returns online-available entries only. When opening a protocol, validate the selected subject against both the public organization and online availability while holding a row lock, before touching the numbering counter. Store the chosen name as a protocol snapshot; never rename existing protocols when catalog labels change. Keep legacy records valid with a nullable catalog reference, and prove that balcão-only and cross-organization subject IDs leave numbering unchanged. For immediate receipt issuance, every online subject must also have an active destination department configured in the same tenant. Validate that destination before allocating the counter, persist it as the protocol's initial department, and include its name in the receipt created at opening. This proves only the initial destination and receipt; it does not validate complete routing, response, or lifecycle behavior.

Snapshot the **initial department name** separately from the mutable current department ID: a receipt describes the opening destination and must stay stable after `forward` or `dispatch`. A forward-only migration may add the nullable snapshot column, but do not backfill legacy rows from the current department because prior routing makes that inference unreliable; legacy receipts with no known opening destination should omit the label. Test the real PDF before and after routing, and test a legacy row remains without an invented destination. Give `forward` its own validated request DTO with required `destinationDepartmentId`; its body and destination must fail with HTTP 400 when absent. Keep `receive`, `dispatch`, and `complete` body optional when their behavior does not require a destination, and align OpenAPI with these action-specific contracts. Add a negative Testcontainers case for each transition under a different tenant, asserting HTTP 404 and unchanged state, department, and event history.

In the subject catalog UI, load destination options from the authenticated tenant-scoped active-department endpoint; do not treat a client-provided department ID as authorization. Keep create/edit drafts separate from saved catalog data and clear organization-specific drafts when the selected organization changes. Render loading, empty, and recoverable error/retry states. Distinguish balcão-only subjects, online subjects with a destination, and online subjects without one; the last state must say that citizen opening is blocked until an active destination is configured. Require a destination before saving an online subject, and keep controls keyboard-accessible with visible labels and concise status feedback. The backend validation and receipt rules above remain authoritative.

For protocol attachments, keep object storage private and expose downloads only through tenant- and authorization-checked API routes; never return bucket URLs or accept a storage key from the browser. Derive object keys from server-generated organization, protocol, and attachment IDs, not user filenames. Validate required per-subject rules, file count, configured size, extension, and content signature before allocating the protocol number. Serialize policy changes against protocol opening so a submitted file cannot be accepted against a concurrently removed rule. Store tenant-bound metadata with composite foreign keys, keep public tracking tokens hashed, and require a valid tracking token or current staff authorization for each download. Bound object reads to the configured maximum, verify stored size and SHA-256 before serving, and count a download only after it succeeds. Treat S3 cleanup after a database rollback as best-effort unless a durable orphan-reconciliation job exists; document that gap. Test with a pinned S3-compatible test double such as S3Mock, but never use that result as evidence of production bucket privacy, encryption, backups, malware scanning, or operational hosting. Keep the supported file-format list explicit and leave unsupported formats pending until implemented and verified.

When multiple `@Testcontainers` methods share one seeded database, scope audit assertions to the entity/action under test or compare a before/after delta; do not assume the tenant has no events from other tests. Any temporary mutation of seeded roles or memberships must be restored in `finally` so a failing assertion cannot cascade into unrelated authorization failures.

For protocol interactions, persist an append-only message with explicit `PUBLIC` or `INTERNAL` visibility and the authoring sector. Serialize public and staff interaction creation plus completion/reopening by locking the same protocol row in their transactions; reject messages from either audience while the UI says re-open first. Test the applicant-message/completion race and assert accepted messages precede the completion event. Recheck sector involvement on staff reads and writes, and apply visibility at both message listing and each attachment download. Test that cross-tenant download returns 404 and changes neither audit nor count. The public tracking token represents only the applicant; do not treat it as identity for additional participants until participant registration and authorization are implemented. Serialize policy update/deactivation with protocol opening using the subject-row lock. Record a successful download in append-only actor/audience audit only after size and SHA-256 verification; serve it with `private, no-store`. Keep opening attachments separate from message attachments in list/count UI, and label them accordingly. `./dev interaction-test` is the repeatable API/Testcontainers plus real-API Playwright proof; it does not validate the official POC, the production bucket, or participant identity requirement `TR91-0524`.

For interaction attachments, generate a staff download route for every message returned by the authorized staff conversation list, including a citizen-authored public message with no department. The staff route must still re-check tenant and internal visibility at download time; the citizen token route remains limited to public files. Store interaction `created_at` using a database clock evaluated at insertion after the shared protocol lock (for example, `clock_timestamp()`), since PostgreSQL `now()` is fixed at transaction start and can reverse visible order when an older transaction waits on that lock. Add a deterministic integration test that starts an earlier transaction, commits a later writer first, then writes the earlier transaction and verifies the displayed order follows insertion order.

For internal attachment downloads, require both an active staff membership and an active department in the endpoint authorization and in the attachment query itself. Test the route and the storage-facing service path, asserting a denied download does not add audit or increment counters.

For histories ordered after serialized writes, avoid PostgreSQL `now()` defaults: it is the transaction-start timestamp, so a transaction that waited for a protocol lock may appear earlier than the row inserted by the lock holder. Upload bytes are currently buffered in memory; treat concurrent public uploads as an explicit capacity-control/ingress-limiting requirement before production, even when per-request limits exist.
